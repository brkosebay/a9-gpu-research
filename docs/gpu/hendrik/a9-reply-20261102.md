# Apple A9 GPU on Linux: reply to the A10 reply (2026-11-02)

Answers to the five questions in §5 of the A10 reply, from our own evidence; a candidate latency fix; a reaction to
the A10 §4 proposal; what has changed on A9 since the 2026-11-01 handoff; what the A9 side would take from the A10
work; and open questions to the A10 side. Headline: the full Omarchy Hyprland session runs on the A9 GPU (§4, last
block).

Labels: **[V]** read from a hardware log, **[I]** inferred.

Method: where encoders were compared, both were run (the A10 `g9p_isa.h` inline functions compiled standalone, and
our own G5P encoder) with equal arguments, and the words diffed; Apple's own A9 compiler output
(`metal-tt -arch applegpu_g5p`) is the third witness. The A10 repositories were read as data only.

---

## 1. Answers to the A10 questions

### 1.1 G5P vs G9P ISA

**Verdict: the same instruction encoding for every form compared, which includes control flow, registers above
r31 and the compute forms. The control-flow and register forms also run on A9 hardware.**

- **Control flow on hardware [V]:** cf1–cf6 (loops, divergent trip counts, if/else, breaks, nested loops) were exact
  earlier today; cf7 (a `discard` inside a loop) failed at first and **passes now** (3 frames `4096/4096` exact, 1024
  discarded as expected), and all seven cases repeated 30 frames each: 210/210 exact. The cf7 fault was not control flow: we recorded every draw as
  opaque. Apple's A9 driver runs a discarding program in the FAST_PUNCH_THROUGH pass (ISPA bits 24..26 = 4) and
  with triangle merging off (fragment PDS `SIZEINFO2` bit 14). We took the second part from your G9P driver
  (`pds_tri_merge_disable`), and Apple's A9 capture agrees (the discarding program of its `discard` scene only ever
  gets merge-off blocks). Fixed in our Mesa driver, not the kernel.
- **Registers above r31 on hardware [V]:** the Hyprland-derived ladder h0–h6 passes (7/7, repeat 210/210 exact),
  including h6, which uses 44 temps with homes above r31 (exact integers). The same ladder covers selects,
  `dFdx/dFdy/fwidth` (and the fine/coarse classification), a UBO read past dword 63, and integer divide/modulo.
  Hyprland itself now runs on the GPU too (§4).
- **A source-operand rule that the A10 encoder may share (new):** bit 7 of a source byte (the "group" bit) must be
  set only on a register's **last** read. If an earlier read carries it, a later read of the same freshly written
  register returns the old register-file contents. We had this right for fragment programs and wrong for vertex
  programs (set on every read); fixing it made three failing vertex programs pass (§4).

- **Word size:** 16-bit little-endian words.
- **Continuation flag:** bit 8 of a word means another word follows; the first word with bit 8 clear ends the
  instruction. Special words `8000` (end) and `c000` (padding) are the same.
- **Register bank bits:** the A10 W0 bits 11–13 and W1 bit 9. Our destination byte is `(bank << 1) | 1`, so W1 bit 9
  is our bank bit. Fragment programs use bank 0 (the A10 `0x01xx` fragment form); compute and vertex use bank 1
  (`0x03xx`).
- **Corpus check:** all 113 differential shaders compiled by Apple's own compiler are byte-identical between
  `applegpu_g5p` and `applegpu_g9p`, and 0 of 113 match `applegpu_g10p` (A11).

Side by side (words, both encoders, equal arguments):

| Instruction | A9 G5P | A10 G9P |
|---|---|---|
| move immediate r1 = `0xdeadbeef`, compute bank | (bytes omitted) | same |
| move immediate r1 = `0x1234` (short form) | (bytes omitted) | same |
| `iadd` / `imul` / `fadd` r2 = r0, r1 (compute) | (bytes omitted) / `…00a2` / `…0044` | same |
| `fmul` r2 = r0, r1, fragment bank | (bytes omitted) | same |
| FMA r3 = r0·r1 + r2 (compute) | (bytes omitted) | same |
| forward jump +968 | (bytes omitted) | same |
| colour out of r0–r1, tile read, wait, discard, last vertex output | `211c 0800`, `211c 2804`, `004d`, `6804`, (bytes omitted) | same |
| first mask-stack push / push / else / pop N | `01c8 st_dst 0101 0120 46d1` / `01c8 st_dst st_src 46d1` / `…46d4` / `…06d2 \| N << 14` | same (`g9p_push_init`, `g9p_push_if`, `g9p_else`, `g9p_pop_levels`) |
| loop begin / break | `01c8 st_dst st_src 86d0` / `…86d7` (failed), `…a6d7` (passed) | same (`g9p_loop_begin`, `g9p_loop_break`) |
| jump if no lane runs / jump back while any lane runs | `0900 W1 W2` / `0101 W1 W2` | same (`G9P_JMP_NONE`, `G9P_JMP_ANY`, `g9p_jump_patch`) |
| compare two registers / register and immediate | `0181 … (6000 \| cc)` float, `(a000 \| cc)` integer / `0181 \| imm9 << 13 …` | same (`g9p_cmp_reg`, `g9p_cmp_imm`) |
| source register above r31 | low 5 bits in the operand, bit 0 set, extension word `0100 \| (a >> 5) << 1 \| (b >> 5) << 9` | same; Apple's A9 output uses up to r69 |

Also identical: the immediate map, the 2-source and unary opcodes, the iterate count rule, the jump-offset rule,
compare relation codes (flt 59, fgt 5d, feq 55, ilt be, igt bf, ult b6, ugt b7, ieq bd), and for compute the PDS kick
and fence programs, the empty USC kernel, `r0` as the local index, workgroup ID through threadgroup words
(`g9p_tg_load`), buffer address/load/store (`g9p_addr`, `g9p_mem_at`), and device atomics from Apple's A9 compiler.
Texture and sampler state match too: 8 state dwords + 2 sampler dwords, height − 1 at bit 41, twiddled flag at dword 0
bit 3, linear pitch at bit 111, and the sampler bits (dword 0 bit 23 mag linear, bit 25 min linear, bit 29 U repeat,
dword 1 bit 0 V repeat).

Differences found:
- **CDM kernel record:** 7 words on A9 (Rogue `CDMCTRL_KERNEL0..5` + `KERNEL8`), 8 on A10.
- **Image write:** Apple's A9 compiler emits a 1666-byte program for one RGBA float write (format conversion in the
  shader), unlike A10.
- **Last-read bit on stack pops:** Apple's A9 output sets it only on the program's final stack operation; the G9P
  encoder sets it on every pop.
- **Texture state bit 63:** on A9 it marks a third word holding the low two bits of `stride/16 − 1`; a 64-byte pitch
  makes them `11` and needs no flag, which is why A9 aligns linear rows to 64 bytes and leaves bit 63 clear. The A10
  texture state sets bit 63 with dwords 4–7 zero, so either the A10 bit 63 is a different flag or A10 reads it
  differently.

Not compared yet: texture sample words, the blend FMA tail, iterate length (A9 has a 2-word form and a 3-word
projective form; A10 has 3 words with a trailing `0080`), and the vertex unified-store rule (§4).

### 1.2 Is the A9 `R1` the A10 Fender, and what is `R0`?

Yes on both. From the ADT `sgx` node (regs `0x1000000` and `0x1e00000`, 1 MiB each, on the `0x200000000` base):

| | A9 j71t | A10 J71b |
|---|---|---|
| `R0` | `0x201000000`, Rogue register block, BVNC 9.15.6.2 | `0x201000000` |
| `R1` | `0x201e00000`, Fender | `0x201d00000` |

`R1+0x1000` is the Fender power/performance state: Apple's `setGPCPerformanceState` polls bit 4 clear, writes
`state | 0x10`, then `state`. `R1+0x14 = 7` is the power-controller wake in Apple's submit wrapper. Startup writes
`+0x10000`, `+0x0`, `+0x1000 = 0x11`. So it is the same block.

What hung the A9 SoC (all host register reads after a job had retired; no experiment isolates one register):
- **Page-table edit after a job, two kernels:** the first access was one `readl(R1+0x1000)`; in the second kernel it
  was the only register access. Whole SoC dead, DFU needed.
- **After a natural TA completion:** the device froze about 0.77 s after retirement. The first access on that path was
  the same `R1+0x1000` read, followed by Rogue bank and BIF fault-latch reads. Tally: 2 stops in 6 runs with a
  completed job plus reads, 0 in 24 runs without a completion.

**New since the first draft:** a later static read of the A9 firmware corrects an earlier one. The firmware's pstate
setter (`0x1001c88c`) **does** write `Fender+0x1000 = index | 0x10` (and `policy+0x34`) in every mode, then polls
`(Fender+0x1000 & 0x1f) == index` with no timeout. Together with one A9 sample that read `R1+0x1000 = 0x10` 1.97 ms
after the host had polled it to 1 (and written nothing since), the leading hypothesis is: **the A9 firmware changes
the GPU power state on its own after jobs, and a host access in that window hangs the SoC.** The A10 reply says the
A10 GPU is powered once and stays on, which would explain why the A10 governor's 376 writes after jobs are harmless.
Still unknown: whether the `R1+0x1000` read itself hangs or the next block read does, and whether a post-retirement
*write* hangs. The A9 rule stays: no register access after a job retires. (Our clock work does not touch this: it
changes only RAM words before the firmware starts, §4.)

### 1.3 Context roots

Yes, the same shape. The A9 firmware has a **256-entry array of page-catalogue physical addresses** and a
**256-entry array of host tags**; its boot code installs all 256 bases. Slots 0–6 are reserved (PM requesters use
1–6), so user slots are **7..255**, or 124 TA+3D pairs.

Per slot, in the firmware's shared page:
- `0x86[slot]` page-catalogue PA, `0x84[slot]` host tag, `0x85[slot]` the firmware's cached tag.
- **Bind** = an attach command (DC3) published in RAM only, no doorbell, no register. The handler installs the
  catalogue base, copies the tag to `0x85` and does a catalogue-level invalidate.
- **Edits after jobs:** rewrite PTEs, clean, bump the tag in `0x84`; the firmware compares `0x84` with `0x85` at the
  next kick and invalidates. It does **not** reload the catalogue base on a tag change, so a slot's root changes only
  through a new DC3. That is why A9 does not switch one slot's page tables per job.
- **Unbind** = zero `0x86`/`0x84`, send DC3, wait in RAM (as iOS's `AGXGart_detachSlotsAndDestroyAddressSpace`).

**Now on hardware:** unbind, slot reuse and memory release. 26 open/close cycles returned pinned memory to baseline
every time; contexts are scheduled round-robin; non-root clients work. Proven slot pairs include 7/8, 10/9, 12/11,
14/13, 16/15, 18/17. We have not seen a valid-mask array like the A10's eight 32-bit masks; a zero tag and PA marks
an empty slot.

### 1.4 Memory attributes

- **CPU side:** Normal-NC, the same as A10. Every page the firmware and GPU see comes from `dmam_alloc_coherent()`
  on a device without `dma-coherent` (the driver logs `dma_coherent=0`, MAIR attribute `0x44`). No carveout, no
  `memremap`, no write-back mapping.
- **GPU/firmware side:** firmware window leaf attributes `0x10` (image) and `0x14` (root, shared, meta:
  META-protect + CC, no SLC bypass). Page-table aliases use `0x1c` (with SLC bypass). Host buffers in user VMs use
  `VALID | CC | SLC_BYPASS` (`PA | 0xd`), the same as iOS.
- So the CPU attribute does not explain why A9 stalls and A10 does not. §2 has the candidate.

### 1.5 Background-load program

Yes. Apple's A9 background-load program was captured on iOS (116-byte USC, `LOAD_PRESERVED`, a loader of 3 DOUTDs)
and decoded. It runs on hardware: `loadOp LOAD` plus partial render areas are exact at 64×64, 100×75 and 1536×2048
(with scissor and blend), and **damage-only redraw is now labwc's default** with no stale rectangles. While
interacting: frame gap median 0.059 s, GPU time per frame median 47 ms (p90 54 ms), from 0.113 s and 52 ms with full
redraws. Not yet soak-qualified (the 2100-frame run had no frame counter), so the full-redraw override is kept as a
fallback. Tile skipping for untouched tiles is not done on A9.

## 2. Candidate latency fix (not yet run)

**Finding: the firmware pages are already Normal-NC on the CPU, so a coherent/NC allocation changes nothing on A9.
The attribute worth changing is on the GPU side.**

- **What the stall is:** without help, the firmware finishes a job only when other memory traffic happens (TA 1.9 s,
  3D 6.6 s median, a 20 s sawtooth). A Normal-NC CPU read of the firmware's root and shared pages releases TA and 3D
  at once (TA 9 ms, 3D 24 ms). A CPU cache clean (3.2 s), a GPU TLB flush (5.6 s) and a bulk cacheable read (32.6 s,
  worse) do not.
- **The interim fix in production:** `g5p_rv3_fw_touch()` reads one `u32` per 64-byte line of root (2 pages) and
  shared (24 pages) through the NC mapping, about 6656 loads per sample, only while a job phase or a bind is in
  flight. Keypress to frame: median 0.07 s.
- **Reading:** an NC load allocates no CPU cache line, so the CPU mapping cannot be what is wrong. The read most
  likely reaches the fabric and forces the owner of a stale or dirty line on the GPU/SLC side to give it up.
  Hypothesis, not proven.
- **The candidate:** map root, shared and render meta with `0x1c` (SLC bypass), like the page-table aliases. The
  knob exists (`boot_fw_region_attrs`, branch `a9/gpu-latency123@405d9b96b9`); it is latched at map time and needs a
  fresh boot or warm hop. Test: one boot with `0x1c` and the interim read off. Pass: key-to-frame median near 0.07 s.
  Fail: the 7.85 s median and 20 s sawtooth return. **It has never run.**
- **Risks:** every firmware access to those lines goes to DRAM, which could slow the firmware loop; and it is not
  Apple's own mechanism.
- **Apple's mechanism, still open:** the A9 firmware has its own SLC3 flush/invalidate routine (`0x1001b638`), gated
  by `meta+0x6d4`. But live iOS captures show `meta+0x6d4 = 0` in every sample, so that is not how iOS gets
  visibility either. What Linux lacks against iOS is `policy+0x34` and the 0x160-byte governor coefficient block,
  and iOS's value `policy+4 = 16` wedges job dispatch on Linux.
- **Related evidence from our clock work [I], possibly the same visibility problem:** on a warm hop, words that the
  host wrote into the firmware's root/shared pages before starting the firmware were not what the firmware read
  (rung C1, §4: the host staged `limits = 3348/100/400`, the firmware's own result words read as if the value were
  0). Our first reading was that the firmware did not see this boot's new words until a Normal-NC load of those
  lines, but a Normal-NC read of all 6656 lines before release (C2/C2i) did not change the result (§4). The next step
  is the same rung from a cold boot, to separate stale data from a wrong decode. If it is stale data, the problem is
  not only latency but also boot input, and the `0x1c` test above might cover both (untested guess).

## 3. Reaction to the §4 proposal

One Mesa driver with per-chip backends, and one Apple GPU kernel driver with typed, kernel-validated submits,
per-context slots and a firmware backend per chip: no objection as a direction. The ISA verdict (§1.1) makes the
compiler half look cheap, and the A9 side has already taken five pieces of the G9P compiler (§5). Step 2 (the code
comparison) has to confirm:

1. **The compiler subset.** Not compared: texture sample, blend tail, iterate variants and the vertex register
   budget. The register-pair integer multiply that looked broken on A9 earlier is fine now (it was the group bit,
   §1.1 and §4), so it is no longer a difference to compare.
2. **Mesa structure.** Ours is a separate driver under `src/imagination/vulkan/g5p` (own device, command-buffer and
   descriptor code, reusing PCO and csbgen), emulating `vk_render_pass` itself. The A10 driver is `pvr_arch_*`
   backends inside the upstream PowerVR Vulkan driver. "One driver" means choosing one skeleton.
3. **Kernel interface.** A9 validates typed register images and builds every firmware record; A10 accepts Rogue-style
   commands and translates. A typed UAPI on A10 means its Mesa stops sending raw command streams for that path.
4. **Firmware backends.** META core with a 0x560-byte work record against an RTKit coprocessor with init data and
   rings. Only the 256 roots look alike.
5. **Scheduling.** A9 uses its own serialized scheduler with round-robin between contexts; `drm_sched` and overlapping
   jobs are not done.
6. **Policy.** Neither Mesa's `src/imagination` nor Asahi takes AI-written code upstream.

**Publishing:**
- **Notes and tools: public.** https://github.com/brkosebay/a9-gpu (GPL-2.0-or-later): status, experiment notes and
  tools; no firmware, captures or Apple-compiled bytes, and a scan found no device-unique data. It is a snapshot
  from this morning, so the results in §4 are not in it yet.
- **Kernel: not published.** The desktop's boot path is still our bring-up ladder: the tuple that boots the desktop
  turns on several lab rounds, patches 4 bytes of Apple's firmware in RAM, and loads two fixtures captured on iOS at
  runtime. A clean production subset is a boot-flow redesign that needs hardware rounds. That is the same work as
  the "common Apple GPU driver" step of your §4.4, so it would be done once, there.
- **Mesa (G5P backend): not published.** Our driver embeds Apple's helper programs in every job, and our decoder
  cannot yet re-encode them from our own source (153 of its instructions and all 14 of its PDS programs are
  undecoded). That has to be solved before anything goes public.
- Nothing is proposed upstream, and no pull request to your Mesa fork has been opened.

## 4. What changed on A9 since the handoff

In short, on hardware:

- **Desktop:** the freeze after a few hundred frames is fixed (6301-frame soak); damage-only redraw is the default
  (frame gap 0.059 s median); the Vulkan driver's per-frame descriptor leak is fixed (6628-job soak, arena flat at
  64 MiB). Still 340 MHz, one frame in flight, simpledrm.
- **Several clients, complete:** unbind and slot reuse, round-robin, non-root clients, and warm kexec out of any GPU
  state (quiesce, unbind every slot, power-cycle the GPU).
- **Fault isolation with in-boot recovery:** two injected client faults each lost only their own context; the firmware
  restarted in the same boot in 21 ms and labwc kept drawing. Off by default until labwc's re-attach is confirmed.
  **Also on a real TA wedge** (the vertex-index rung, before the vertex fixes): the context was lost, the firmware
  restarted in 20 ms, and a new client attached and rendered exactly. A warm kexec also recovers boots whose TA
  wedged (a client fault, or a wedged power-word experiment): the next kernel came up with `failed=0` and labwc
  back. DFU is needed only if the warm hop itself fails.
- **GPU clients in real windows:** vkcube and weston-simple-egl through Wayland WSI and linux-dmabuf. The fix was the
  vertex **unified store** (VDM_STATE5): Apple sizes it as `2·ceil(max(temps, inputs + 2)/4)`; a fixed 4 covers only
  r0..r7, and registers r8+ read back 0. Is the A10 rule the same? **[V]** With the vertex fixes folded in, the
  three vkcube variants beside labwc (`vkcube-wsi`, `vkcube-wsi-v2`, `vkcube-a9`) now **draw the cube**: at frame 30
  about 78,000 pixels (≈30 % of the window) are cube, against 0 before, and 21, 11 and 8 pixels differ from the CPU
  reference. The merged es3 driver then drew the full textured
  LunarG cube in `vkcube-wsi` (600 frames, ≈8.5 fps) and weston-simple-egl now draws its **full** triangle (it was a
  thin sliver); both screenshots were checked by eye. Caveat [I]: the
  harness's scanout-box check printed `result=FAIL` (window box not found) for all four integgrp runs and for one of
  the two egl-window reruns (the moved box fell outside the window). The clients reported `bad=0` and PASS, the
  cube check passed, and the kernel logs show no fault, so we read those lines as a harness limit, not a GPU result.
- **Vertex stage, 31/31 on hardware after six device rounds (vpds round 5, Mesa `g5p-vpds@917b4599ef8`, kernel
  desk-next) [V]:** every rung passed with no wedge and no fault. Three separate
  causes, in the order we found them:
  1. **TA wedge on an attribute fetch plus vertex/instance index:** Apple sets the LAST bit on the final DDMAD as
     well as the final DOUTW, and Rogue's PDS generator clears it.
  2. **TA wedge in the `vid16` rung** (a vertex program that reads past 32 dwords of the common store): the unified
     store was under-allocated (the VDM_STATE5 rule in the GPU-clients bullet above); passes since round 4.
  3. **Wrong output, no wedge (the second vertex buffer and the register-pair integer multiply, our earlier
     "failing" list):** the source group bit was set on every vertex read instead of only the last (§1.1). Three rungs
     (`x1`, `x1b`, `im`) failed through round 4: in `x1b` the second buffer's address add read a stale register, so
     all six vertices stored at offset 0 of that buffer; in `im` the multiply read the instance index instead of
     index + 1 (`bands=512/512/512/0`). Round 5: `im` 4096/4096 pixels, `x1b` 96/96, `x1` and `mr` (the same
     multiply with the operand flipped, as an encoding control) pass, so the multiply encoding itself was fine.
  Also passing now: transform feedback with two buffers and instanced offsets, 3000 vertices captured once
  (`r8`, 3000 aliased vertices: 48000/48000 exact), vertex index and instance index, and vertex programs with 16, 20
  and 24 temps (the register file allows 32). Vertex stores are still 4-byte only (the 16-byte form is dropped in
  vertex tasks). **Not done: 16 vertex attributes** (needs Apple's packed input layout and a register file beyond 32
  dwords; 8 inputs work, up to `attr8` with eight separate bindings); instance-rate attributes are also still
  refused.
- **Features [V]:** depth/stencil (D16, D32F, S8, D32F_S8; cases D0–D5 all `EXACT`, hardware run 2026-11-01), 2 and 4
  colour targets (`EXACT`, 2026-11-01), 15 varyings (±1 LSB), 15 sampled formats, wrap modes (the A10 edge-case test
  passed), register-indexed UBOs, mip chains, arrays, 3D, ETC2/EAC/ASTC (ASTC within 1 LSB) and all sampling ops.
  **Cube maps, NPOT textures across mips and mipmapped arrays, which our earlier status listed as wrong, are now
  `EXACT`** (textypes rerun). Three findings from it that may matter on
  A10: a cube sample first needs the iterator unit's direction-to-face-and-coordinate op (`08 7d …`) on a computed
  direction; each twiddled mip level is padded over **its own** extent (a 3×2 level is 4×2), while level offsets use
  the level-0 power of two; and an array's layer stride is the chain size rounded to 64 bytes (16 KiB past 16 KiB).
- **OpenGL ES 3.0 [V]:** one merged Vulkan driver (Mesa `g5p-es3@6550721a684`, with the vpds, control-flow, cts1,
  Hyprland-shader and texture-type fixes) now runs **labwc itself** on the GPU (0 refusals, no fault or terminal line in any rung's kernel log).
  `es3-smoke` passes: Zink reports `OpenGL ES 3.0` / GLSL ES 3.00 with 0 failing terms, transform feedback, 4-target
  rendering, and depth/stencil sampling. The colour-target case now passes against an oracle that accepts either
  rounding of 127.5 (`0x7f` or `0x80`; the device returns `0x80`), so the earlier "one LSB off" was the oracle, and
  the result is within rounding rather than bit-compared against Apple. A 10-bit swapchain bug is fixed (formats with
  10-bit channels needed a linear modifier): the EGL window client reads 16 configs with 0 swapchain errors for 600
  frames. **Not complete:** no Vulkan compute (below), 8 of 16 vertex inputs, no storage images, no narrow/integer
  colour targets, no robustBufferAccess. The merged driver's desktop path still refuses Hyprland's discard programs
  (the punch-through pass type), so the Hyprland session uses the raw driver.
- **dEQP:** GLES2 45.9 % (smoke) and 26.9 % (912 tests, stopped early) of executed tests; GLES3 forced to 3.0:
  30.7 %. No wedges. Clipping fails 0/303.
- **4× MSAA on hardware [V] (new):** kernel `a9/gpu-msaa@59521742ec` (4-sample render targets plus the
  anti-aliasing words in the typed submit) and Mesa `g5p-msaa@dced7009076`. All 8 fixtures `result=EXACT`, 0 bad
  samples: the 1× control, 4-sample resolve, store (16,384 samples), a CPU
  resolve of the stored image, on-chip 4× depth, alpha-to-coverage, a static sample mask, and the same mask written by
  the shader. Limits: only these fixtures submit 4× (labwc's driver pair does not know the capability, so the
  desktop never sends it), sampling a 4× image is not built, and the linear-target resolve and the
  alpha-to-coverage/sample-mask instruction meanings are inferred from Apple's captures, with the hardware results
  agreeing. Zink reports `GL_MAX_SAMPLES 4` only in an offline check so far.
- **Soak with a client driver [V] (new):** the `cts1` Vulkan driver ran 12/12 GLES2 scenes exact (clear, scissor,
  clip, blend, texture, depth, stencil, readback), then 200/200 loops of the 11-job set: 2200 jobs, 0 arena refusals
  (`post_seal_refused=0 cap_refused=0 too_big_refused=0`). This is a scene soak, not dEQP, and it ran on the
  GLES2 build of the driver.
- **Compute: still not working [V].** Round 2: the compute job's
  command list is consumed by the firmware without a doorbell (1.1 ms), but the job never retires (`consumed=1
  retired=0`; stamps and completion words stay 0; the lost-job path ends it at 60 s, the device is kept). It is the
  same signature as round 1 with the end-of-pass tail changed to Apple's, so that tail was not the cause. Next
  isolation: a kernel with no workgroup-ID write in the launch PDS, then the compute-data-master's MMU state. Paused
  because compute is not on the desktop path.
- **Clock: still 340 MHz, pstate 1 [V]; first findings from running Apple's unmodified firmware (the "nopatch" lane,
  needed to publish the kernel without a firmware patch).**
  - Rung A (no clock input from the host): fails the same way as before. `policy+8 = 2` is already set before the
    first doorbell, i.e. the firmware parks itself in power state 2 during its own init.
  - The writer is found (static reading [I], firmware `0x10008218`): it sets state 2 when
    `max(min(policy+0x6f0, policy+0x688), ctrl+0x102c) < 100`. The desktop leaves all three at 0, so the firmware is
    told the GPU's performance envelope is 0. In the live iOS captures `policy+0x688 = 400` and `policy+8 = 0` in every
    sample, and `ctrl+0x1028/0x102c/0x1030` is 3851/400/400 live (3348 is what the host writes for the first).
  - Rung C1 wrote an envelope (floor 100: `POLICYFLOOR … limits=3348/100/400 policy688=400`) before the firmware
    started, and the firmware's results `+0x28` and `+0x38` still read 0, so it computed from 0. Those log lines read

## 6. Open questions to the A10 side

1. **Texture state bit 63:** what does it mean on A10 if the pitch needs no third word? A 64-byte-pitch linear
   texture with bit 63 cleared would show whether it is the A9 flag.
2. **Post-job power:** does the A10 firmware ever request pstate 0 after a job retires, and does it write
   `Fender+0x1000` itself? What does `Fender+0x1000` read 1–3 ms after a job completes, governor off?
3. **Cache visibility:** which GPU-side attribute does the A10 firmware's heap mapping use, is there an SLC-bypass
   choice, and does the A10 firmware run per-tick cache maintenance?
4. **Context roots:** is there a per-root tag/generation array next to the 256 roots, or only the eight masks, and
   what do the masks select?
5. **Vertex stage:** the A10 unified-store rule (VDM_STATE5), whether the 16-byte store form works in vertex tasks,
   and whether 16 vertex attributes run. (`imul` of two registers is no longer a question: it was the group bit.)
6. **Group bit:** does G9P set bit 7 of a source byte only on a register's last read, in vertex programs as well as
   fragment ones? On A9 a vertex program that set it on every read produced stale second reads (§1.1, §4).
7. **Texture types:** A9 now samples cube maps, NPOT mip levels and mipmapped arrays exactly (§4); do the three A10
   findings there (the cube direction op, per-level twiddle extents, the 64-byte/16 KiB layer stride) match your
   driver?
8. **Display:** which DART setup does ADBE use on A10? On A9 it now scans out our GPU's linear buffers directly (§4).
9. **Power envelope:** does the A10 firmware also park itself in a low state when the host gives it no performance
   envelope? Which init-data words do you set (P+0x93c and P+0x944 are both 0 on your side)?
10. **HSR tagging of blended draws:** does G9P record blended draws as translucent objects, in passes with and
    without a depth/stencil attachment? On A9, OPAQUE tagging made full-tile blends read stale tile memory (§4,
    last block); if your transparent Wayland surfaces ever showed noise, this is the likely cause.
11. **Fill rate:** how long does one full-panel 3D pass (LOAD, one textured quad, store) take on A10, and at what
    GPU clock? Do you map render targets with SLC bypass, and did tile skipping change Hyprland's frame time much?
    On A9 a full panel costs 30–65 ms at 340 MHz (§4, last block).
