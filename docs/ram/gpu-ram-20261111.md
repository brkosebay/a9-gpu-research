# RAM2: Orchard 0.4 rc2 RAM audit — 2026-11-11

> **Published extract** of the Orchard 0.4 rc2 RAM audit (2026-11-11): only the GPU parts. These are the
> accounting rules for the one-run census and the ranked design for cutting GPU-stack RAM. The census
> script and the browser comparison are not included. There is **no closed RAM balance yet**. The
> estimates in the table are hypotheses to be measured, not savings, and they overlap, so do not add
> them up.
## One-run census

Implementation: `scripts/ram/ram-census.sh`.
POSIX shell wrapper using installed Python3; stdout only; root needed for
all PSS/debugfs/boot receipts. No debugfs mount, MMIO/register dump, process
stop, swapoff, cache drop or tuning write. Reads one alias of each BO list.
Smaps rollup scan is sequential and can briefly contend with memory activity;
run once per condition, not a tight loop.

Prints full meminfo, nested physical ranges/memblock (if exposed), crash
reservation, running log config and retained early printk receipts, slab and
page tables via meminfo, GPU BO ownership/import/pin records, PSS/RSS/Anon/File/
Shmem/SwapPSS for every readable process, zram payload and effective ratios,
cache excluding shmem, PSI, CPU and reclaim counters. Failures are explicit.

**Limits that require a GPU lane change:** rc2 has no complete current
firmware/private coherent-DMA bytes counter and no kernel mapping from BOs to
winsys suballocation live/committed bytes. Census marks these UNKNOWN; historical
boot receipts are not a live total. Enable `PVR_G5P_ARENA_LOG=1` **on a fresh
client** for `committed_kib/live_kib/data_live_kib` and `slice_live_kib` receipts (0 is still enabled by
this parser; unset to disable). Log to NVMe. No new client launched by census.
A printk config estimate cannot replace a lost early allocation receipt.

Accounting rules: CMA ⊂ MemTotal; Shmem ⊂ Cached; GEM pins overlap Shmem,
Unevictable and mapped PSS; imported scanouts alias ADBE BOs. Sum process PSS
for browser comparisons, but never add it to all GPU BOs as independent usage.
`Cached−Shmem` is an approximate file-cache view; SReclaimable is additional
reclaimable slab, not another copy of Slab. Zram net payload saving is
orig_data_size−mem_used_total, not an amount to add to MemAvailable. iomem
is nested; no naive range sum. Do not reconcile nominal2 GiB using old loader
exclusions without the current bank map. No claim of a closed balance yet.

## GPU RAM design for the Opus lane — no implementation

**Counter correction:** Orchard drm patch0013's close log reads global
`g5p_bo_count/g5p_bo_bytes` and `d->pinned_bytes`. Both `live_bo_bytes` and
`device_pinned` are **device-wide**. A log emitted when each client closes
does not make them per-client. Use patch0012 `g5p_bos` rows (`by=comm[pid]`,
size, handles, imported, vm_pins) plus per-VM receipts. Pins exclude firmware,
PM/private DMA, GPU tables; live BO bytes includes unpinned live BOs.
Thus105–182 MB pins and132 MB live BOs can be different times/owners and
cannot explain a per-client cost without simultaneous captures.

Mesa memory model: arena stores USC/PDS code, command/control and small data
slices in16 KiB pages; larger/dedicated application allocations and display
imports use separate BOs above the code window. Current data allocation has
8 MiB RW chunks; allocations over half a chunk are dedicated. Arena chunks
are executable; a slice's address remains fixed. Logical free slices can leave
physical pages pinned in partly live chunks. Tail-only trimming cannot remove
an empty interior chunk behind a live tail; first chunk is kept.128 MiB is
fallback or an environment override; inspect `/proc/PID/environ` for overrides.
Do not lower this cap blindly: prior STK failures demonstrated capacity needs.

**Apple first, rechecked in shared Ghidra this session:**
`AGXParameterManagementMeta_growPoolFromFirmwareFeedback`,
`fffffff006cb09bc` (command: `python3 scripts/ghidra.py decompile_function_by_address address=fffffff006cb09bc`).
The decompile consumes PM feedback at list+0x40, rate-limits updates, computes
an RT-dimension floor, applies128-job hysteresis when reducing that floor,
and links allocations in0x20000-byte blocks, bounded by PM caps. The code is
feedback-driven, rather than evidence for freeing a PM pool after a guessed
number of retired jobs. Lowering the floor here is not proof the function
actually frees existing blocks. Its decompile uses4 KiB units for some feedback;
do not substitute Linux16 KiB blindly.

Existing RE PM lifetime
shows fragment release drops descriptor/context references, not the PM free
list. Firmware host requests
documents type7 allocation requests and command9 replies; historical captures
did not contain such a request. This establishes protocols and lifetimes,
not an iOS per-browser memory total or arbitrary purgeability of all BOs.
No claim Apple uses our monolithic executable arena, or that iOS memory can
be transplanted unchanged.
