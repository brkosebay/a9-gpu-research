## 2. GPU performance states: where they come from and who selects them

Chain, all **[P]** unless marked:

1. **LLB writes the table into PMGR**: 5 PSINFO records at `0x20e070000 + 0x10·n` (LLB
   (boot-firmware address omitted), from the PLL descriptor table at (boot-firmware address omitted)). Word 0 = core DAC code [31:24] |
   valid [21] | mult [20:12] | prediv [8:4] | postdiv−1 [3:0]. Word 1 [7:0] = buck8 code. Word 2 =
   timing selectors. The live records (`clock-mechanisms.md` §2.2) are 340/474/550/723 MHz; record 4 =
   `8a2f1041`/`7c` = 881.25 mV core, 987.5 mV buck8.
*(Passage removed: boot-chain or iOS-side tooling detail, out of scope for this repository.)*
3. **m1n1 `0011-kboot-Fill-the-A7-A11-GPU-s-performance-states`** fills the `gpu` node's empty
   `operating-points-v2` table from `sgx/perf-states` (opp-hz, opp-microvolt, opp-level = state).
   **On our DT it does nothing:** the G5P node (`gpu_diag`, `compatible = "gpu,s8003"`) has no
   `operating-points-v2` (checked in the running `j71t.dtb`), and the G5P driver reads no OPPs. The
   driver uses its own table `g5p_perf_mhz = {0, 340, 474, 550, 723}` (`perf-envelope.h`) and the
   PSINFO records directly.
4. **Selection.** Hardware applies record *n* when Fender is asked for pstate *n*
   (`R1+0x1000 = n | 0x10`). Neither the host nor the firmware writes PMGR or the PMIC for a
   transition (ds-gpu-dvfs §3.4, Derived but the only reading consistent with "no host writer, no
   firmware PMGR mapping").
   - iOS kext: `AGXMetaFender_setGPCPerformanceState` `0xfffffff006ca4ccc` (re-decompiled today:
     poll bit 4, then `Fender+0x1000 = state | 0x10`, ~2 s budget, then panic). The kext writes only
     states 0/1. The META firmware governor (`0x1000aa80`, setter `0x1001c88c`) picks the state from
     `meta+0x710..0x754` (table) and `ctrl+0x1028/0x102c/0x1030` (limits). The host can only cap it:
     `AGXAccelerator_setPerformanceLimit` `0xfffffff006c9a74c`, driven by CLTM/PPM strings.
   - **New today:** `0xfffffff006c819cc`, renamed **`AGXAccelerator_buildPstateV2FTable`** in the
     shared project. It panics unless the pstate count at `+0x1c4c` is 1..16
     (`max_pstate < AGF_MAX_NUM_PMGR_PERF_STATES`, string `0xfffffff0059437d8`). For every state it
     stores (mV/1000)² × MHz, from `+0x1c94` (mV) and `+0x1c54` (Hz): the kext's own C·V²·f power
     model. So **a sixth state is inside Apple's 16-slot design**, and power scales with V²·f.
   - Ours (opt1): firmware policy pinned, `ctrl+0x1040 = pin 400` and seed q=4; the release powers
     on at `R1+0x1000 = 0x14`. The overclock does the same with pin 500 and q=5: record 5 is written
     while the GPC is still at state 1 (map time), the firmware's table and limits are extended to
     index 5 (`g5p_perf_oc_extend`), and the release powers on at `0x15`. The pstate never changes
     under a live firmware.

**Prior device evidence (release8, 2026-11-03) [P]:** record 5 at 948 MHz at stock state-4 voltage
was flown. CR_TIMER × 256 read 948.0 MHz (722.7 at state 4). ALU time ratio was 0.772 against a
clock ratio of 0.763 (`release8-notes.md` §"Measuring the GPU clock"). So the PLL is in force, and
948 at +0 mV ran that ALU job. A full stability/benchmark set was **not** recorded at any rung. The
glmark2 heavy set was flat from 723 to 852 MHz, so the desktop is latency-bound, not clock-bound.

## 9. GPU clock encoding and the ceiling (d6500232ce7, 2026-11-10)

### 9.1 Where the GPU clock is set

**[P]** the record layout and field widths below (LLB packer, iBoot decoder, all five live records
decode exactly), and that a record-5 PLL is in force when Fender runs state 5 (release8: CR_TIMER
read 948.0 MHz for a 948 MHz record). **[Derived]** (`ds-gpu-dvfs.md` §3.4) that nothing else sets
the GPU clock: no host or firmware PMGR writer exists, so the hardware applies the **PSINFO record**
of the state Fender is asked for (§2).

| what | address | evidence |
|---|---|---|
| PSINFO record *n* word 0 (core DAC, valid, PLL) | PMGR `0x20e070000 + 0x10·n` (driver: `G5P_PSINFO_REC(n)` = PMGR syscon `+0x70000 + 0x10·n`) | LLB, iBoot, driver readback |
| kext power model | `AGXAccelerator_buildPstateV2FTable` `0xfffffff006c819cc`: Hz per state at `+0x1c54` as **u32**, ≤ 16 states | Ghidra (shared project) |
| the request | Fender `R1+0x1000 = state | 0x10`; poll bit 4 clear and nibble = state | driver, kext `0xfffffff006ca4ccc` |

### 9.2 Formula, widths, ceiling

```text
f_GPU = 24 MHz * mult / prediv / postdiv        VCO = 24 MHz * mult / prediv
mult    = word0[20:12]  9 bits  0..511 (0 = no PLL)
prediv  = word0[8:4]    5 bits  1..31  (0 decodes to 0 Hz)
postdiv = word0[3:0]+1  4 bits  1..16
encoding ceiling = 24 * 511 / 1 / 1 = 12264 MHz   (VCO 12264 MHz)
```

All five live records decode exactly with these fields (723 = 241/4/2, 550 = 275/4/3, 474 = 79/2/2,
340 = 85/2/3). Apple's GPU descriptors use prediv 1..6 and postdiv 1..4 (800 MHz = 100/3/1 has
postdiv 1). **12264 MHz is the fields' maximum, not a claim that the PLL locks or the GPU runs
there** (the same caveat as the CPU's 12264 MHz in overclock-round6.md; same 24 MHz reference, same
9-bit multiplier).

Ceilings on the way, for the record:

| bound | value | applies to us? |
|---|---|---|
| record 4's dividers (4/2) | 1533 MHz (mult 511) | the first band's end |
| prediv 2, postdiv 2 | 3066 | band 2 |
| prediv 1, postdiv 2 (Apple's 804/900 dividers) | 6132 | band 3 |
| prediv 1, postdiv 1 | **12264, the encoding ceiling** | band 4 |
| Apple's software Hz fields (iBoot, kext `+0x1c54`) | u32 Hz: 4294.967 MHz | no: iBoot runs before record 5 exists, and we don't run the kext |
| our firmware MHz table `meta+0x718[5]` (u32 MHz) and its TXTIMER reload consumer (`MHz * 0x3e8 >> 8` at `0x8000a1ac`, `dsx-r71-init6c0-runtime.md`) | 12264 * 1000 fits 32 bits | no overflow in that consumer [V, from the documented disassembly]; other firmware readers of `priv+0x2c4` are not audited [I] |
| Apple's largest shipped GPU multiplier | 425 (850 MHz, `0x23`) | **confound:** 1278..1533 MHz uses mult 426..511 at 4/2, a multiplier Apple never ships. A lock failure there need not be the VCO limit. Apple's 804/900 dividers (1/2) give the same clocks on a 12 MHz grid with mult 107..127 (f = 12·mult), but this grid always picks 4/2 below 1536. If the ladder stops in 1278..1533, a follow-up kernel can offer the 1/2 encoding at the same MHz to separate multiplier from VCO |

### 9.4 What else changed in the kernel

- **Power-on failure latch.** If the release's state-5 poll times out (10 ms, `-ETIMEDOUT`: no PLL
  lock, or Fender refused), the kernel logs `GPUPERF oc poweron-failed mhz= r1_1000=` and every later
  map of the boot runs state 4 (`GPUPERF oc off why=poweron-failed`), like the thermal stop. Before,

- **Status line always logged.** `GPUPERF oc status … r1_1000=` (every 10 s while overclocked:

  correctness failure on that rung, never for a thermal/clock/setup stop), arm < 85 C, stop at 90 C,

### 10.1 GPU: the 90 C stop becomes a throttle

The 500 ms poll (`drm-render-v3.inc g5p_oc_work`) reads the three SoC zones. The decision is a
pure helper, `gpu-oc.h g5p_oc_decide()`, covered by the host test:

| condition (hottest zone) | action |
|---|---|
| first map of the boot, ≥ 85 C | wait at 723 MHz (`GPUPERF oc wait why=hot`), step up once below 85 C. Before §10 the overclock stayed off for that epoch. The overclock still engages only below 85 C. |
| ≥ 90 C, ≥ 2 s since the last step | **one step down**: 24 MHz (one ladder step), snapped down onto the PSINFO grid (850 → 825, 900 → 876), never below **723 MHz** (state 4, record 5 cleared) |
| 85..90 C | hold (hysteresis) |
| < 85 C, ≥ 10 s since the last step | **one step up** toward the request, never above it |
| ≥ **105 C**, or a zone unreadable | **hard stop**: 723 MHz for the rest of the boot, and `apple_a9_thermal_revert()` reverts an armed CPU tuning too |

**What a step costs.** Record 5 is written only at the firmware map (the GPC at state 1), and the
pstate never changes under a live firmware (§2). So every step is a **planned relatch**: the render
scheduler parks the GPU between jobs, cycles the gate, boots the firmware again, and the `map` stage
writes record 5 at the new clock. This is the in-boot recovery (`g5p_rv3_recover()` → core
`g5p_recover()`), so every context survives and is re-bound by its next job. **One step = one firmware
reboot**. The line `GPU-RECOVER why=oc-throttle … ms=` gives its duration; it is not measured yet.
- Each relatch keeps the old epoch's `struct g5p_boot` allocated (a few hundred KiB, by design in
  `recover.inc`). A boot therefore gets at most **64 relatches**, and the 64th always goes to 723 MHz,
  which bounds it to about 20 MB.
- A relatch is still a new epoch (`recoveries` stays the PM epoch id), but it counts neither toward
  the fault budget (`G5P_RU_RECOVER_BOOT_MAX`) nor the streak.
- `946bd3f3bcd`: a fault on the first job of a relatched epoch recovers like any later epoch's.
  Without the fix it looked like the boot's first epoch, which is terminal. The behaviour is
  identical when nothing relatched.
- A fault recovery clears a pending relatch flag.
- A request that a recovery already under way could not take is asked again
  (`GPUPERF oc relatch-again`).
- A throttled epoch keeps the rung's rail voltage.
- **[I]** This planned path (no lost job, under load) is the old 90 C stop's recovery, which never
  ran on hardware either.

**Lines.**
- At the map: `GPUPERF oc on mhz=<in force> req=<request> … throttle_at=90000 hard_at=105000 step=24`.
- At the map when throttled to the floor: `GPUPERF oc throttled mhz=723 req=…`.
- At each step: `GPUPERF oc throttle down|up from= to= req= temp= zone= relatch=n/64 throttled_ms= run_ms=`.
- At the hard stop: `GPUPERF oc hard-stop temp= zone= …`.
- After each relatch: `GPU-RECOVER why=oc-throttle` and `RENDER-V3 oc-relatched … why=oc-throttle`.
- Every 10 s the status line adds `req= eff= throttled_ms= run_ms= down= up= relatches=`. The ladder
  checks its Fender state against `eff`: state 5 above 723 MHz, state 4 at 723.

### 10.2 CPU and the DT trips: `apple_soc_cpufreq.a9_hard_millic` (opt-in)

There is a new parameter, `a9_hard_millic`: 0 (the default) is off; otherwise it is clamped to
100000..105000. It selects the **throttle profile**, with or without `a9_tuning`. The round-6
profile lived in `apple-a9-tuning.h apple_a9_get_thermal_profile()`: passive `a9_passive_millic`, hot
95, critical 100. The trips are applied by `drivers/thermal/apple_s8003_thermal.c a9_apply_profile()`
and checked by `a9_thermal.py`.

| profile (`profile=` in `a9_thermal/snapshot`) | boot args | passive | hot | critical | CPU guard at passive |
|---|---|---|---|---|---|
| `stock` (no args; the base entry) | none | 80 | 90 | 100 | no guard |
| `sustained` (round 6) | `a9_tuning=1 a9_passive_millic=90000` | 90 | 95 | 100 | revert + latch |
| **`throttle`, GPU rungs** | `a9_passive_millic=90000 a9_hard_millic=105000` | 90 (cpufreq cooling) | **105** | **105** | no guard: CPU stock |
| **`throttle`, CPU rungs** | the same + `a9_tuning=1` | 90 | **105** (guard revert) | **105** | **cap at stock 1800 MHz** (slot, heartbeat and checks kept), lifted below 85 C |

- The trip driver still validates the unmodified DT first (80/90/100; the running `j71t.dtb` has
  exactly these). Only the throttle profile moves the critical trip.
- Every `make-oc-entry.py` rung entry now carries the throttle profile:
  - `--round6-thermal` keeps round 6 (CPU only);
  - the base entry stays stock;
  - **the stock kernel without these args is unchanged**.
- The guard status line adds `throttled= throttles= throttle_ms=`. `ladder.py hold` records
  `throttled_fraction` and `throttle_ms` in `hold-done` instead of failing.
- `a9_thermal.py` accepts the `throttle` profile and lets trials and holds read sensors up to the hard
  limit instead of passive. A round-6 trial that the guard caps still fails delivery (10 s), as before.

**What 105 C does on a rung boot.**
- With hot = critical = 105, the hot trip reverts the CPU tuning.
- The critical trip then runs the thermal core's orderly shutdown (`thermal_zone_device_critical`),
  as at 100 C on every boot before.
- The GPU's own hard stop polls every 500 ms; the thermal core polls every 100 ms. So at 105 C the
  device most likely **powers off**: the host sees no return and gives the DFU/cold-boot
  instruction (§7.3).
- No trip above 105 was invented.

### 10.3 Risk

- **Sustained 90–105 C on a passively cooled iPad.**
  - The throttle holds the SoC near 90 C for as long as the load lasts; the hysteresis is 85..90.
  - Before, the ladder stopped there. Now a rung can sit at 90–105 C for its whole duration
    (≈ 15–30 min).
  - iOS's CLTM throttles far earlier.
  - Nothing here measures the battery, case or display temperature. The SoC sensor is not the
    battery's, and lithium cells age fast well below these numbers.
  - The long-term silicon effect of +V at 90–105 C (electromigration, BTI) is unknown.
  - Watch the case temperature on the first throttled rungs. The owner can stop at any time.
- **A 105 C poweroff looks like a no-return** to the host, which prints the freeze/DFU instruction.
  To tell them apart: the last lines of `/var/tmp/oc-ladder/<tag>/temps.log` (its 2 s samples near
  105000) and the next boot's pstore/netconsole (`thermal … critical temperature reached`, an orderly
  poweroff) versus a lock with no shutdown messages.
- **Rungs now end hot.** The host waits idle before each hop until every zone reads below 75 C
  (`cool()`, up to 15 min, then it hops anyway). The rung waits again for below 80 C (`COOL_S`,
  900 s). That wait is not a stop; it ends as an error only if the device is still hot after it.
  A first map at 85 C or more starts at 723 MHz (`oc wait why=hot`); the rung then stops as setup
  ("cool before the hop") instead of spending relatches stepping up.
- **Shutdown moves from 100 to 105 C** on rung boots (critical trip).
- **The trip-profile path without `a9_tuning` runs for the first time on Orchard** (every GPU rung).
  - If the trips do not validate, the thermal probe fails. The zones are then missing, the GPU
    overclock refuses with `zones-unreadable` (a setup stop), and that boot has no thermal zones.
  - On the first rung, check
    `grep . /sys/class/thermal/thermal_zone*/trip_point_*_temp` (expect 90000/105000/105000).
- **Each step is an unflown firmware reboot under load.** A failed relatch ends the GPU epoch
  (`RENDER-V3 recover failed … planned=1`) and is a stop (rc 6). It is never retried with voltage.
- **Comparisons:** the base and the stock controls boot the stock entry (CPU passive 80 C); the rungs
  boot with passive 90 C. This barely matters for GPU-bound scenes, but CPU cooling throttles
  earlier on the base.

### 11.2 Where the EIO and EBUSY come from (`946bd3f3bcd`, read in full)

**Submit (`g5p_render_submit_admitted()`).** These are the only `-EIO`/`-EBUSY` returns that
printed nothing:

| check | errno | state that trips it |
|---|---|---|
| `b->failed && !g5p_rdev_ruling()` (top of the call) | -EIO | the epoch's failed latch, with no job executing and no recovery pending |
| `c->bad \|\| r->detached` | -EIO | a job of this context failed after touching the hardware (`g5p_render_run()`) |
| `g5p_render_device_claim()`, device claimed | -EIO | failed or stopped epoch |
| `g5p_render_device_claim()`, first claim | -EBUSY | core lock busy, or a claim precondition |
| `r->queued >= G5P_RU_MAX_QUEUED` | -EBUSY | queue full |
| `g5p_render_result_slot()` | -EBUSY | oldest retained result still pending |

`g5p_rv3_admit_submit()` already logged.

**Render target (`g5p_create_render_target()`).** The EBUSY comes from `g5p_render_vm_idle()`:
- the busy branch: bad, detached, jobs queued, or `rdev->recovering`. This one warned, as `G5P
  VM_BIND busy=render-idle`. Look for that line in the +0 mV boot's dmesg: the ALU run is a fresh
  process, so its context is unbound, and only this branch (or `xa_alloc`) can refuse it.
- `r->bound && b->failed`, where the result depends on the ruling: -EBUSY while ruling, else -EIO.
  This branch was silent.

**The failed latch was set in many places with no line at all:**
- the R73B aux-ring drain (an index above 255 → -EPROTO), and every other error in
  `g5p_r73b_service()`;
- the R73B lifetime IRQ cap (epochs without heartbeat116);
- the event drain's lifetime limit (-EOVERFLOW without heartbeat116);
- the legacy IRQ drain error;
- a failed firmware map (`g5p_boot_maps()`) or boot command;
- a failed lifecycle command;
- a failed recovery;
- a failed detach.

If the latch is set while no job is in flight, nothing runs that would print. The next submit then
gets -EIO from the first check, without any line. That matches the repro exactly: the passes=2 run
completes, the latch goes up between runs, and the passes=8 run's first submit is refused
(`accepted=0`).

A job that fails *on the hardware* prints a line. Timeout, fault, lost or recovered: each prints
`RENDER-V3 lost/terminal/no-recover` or `GPU-RECOVER` (`g5p_rv3_terminal()` also prints a later
failure after the epoch's TA-complete latch, once, as `failed=1 admission=closed`). A context lost
that way then refuses its next submit through `c->bad` with the same silent -EIO, so the repro alone
does not tell the two apart.
- The orchestrator saw no kernel line at all, which points to a silent latch.
- The ladder's `faults: []` is weaker evidence. Its regex (`RENDER-V3 slow|lost|fault`, `recover`)
  did not match `RENDER-V3 terminal`, and it only reads the rung's own dmesg window.
- The regex now also matches `terminal|no-recover|refused`, `end=fail`, `end=refuse` and `HB116
  trip` (`scripts/power/oc-ladder.sh`, in the packet).
- Either way, the new lines name the site (`fail_site=`, `ctx_bad=` with `bad_ret`/`bad_job`).

### 11.3 Why it depends on the clock: not identified on the host

- **No budget, limit or deadline in the DRM driver is derived from the GPU clock.** Every DRM
  driver file was searched for MHz/Hz/pstate/723 uses. The only hits are the overclock's own policy
  and its thermal poll.
- **The core writes one clock-derived value at every firmware map:** `g5p_perf_oc_extend()`
  (`perf-envelope.h`, from `2545d44d1a5`).
  - It writes `meta+0x710 = 5` (max index), `meta+0x714 = 6` (count) and `meta+0x718 + 4*5 = MHz`.
    That is the firmware's MHz table, which Apple's `6c974f0` exports as `[0,340,474,550,723]`
    (docs/power/README.md).
  - It also writes `control+0x1030/0x1038 = 500` and `policy+0x688/0x68c = 500`.
  - The rung's map line shows the result: `table=5/6/0,340,474,550,723 limits=3348/500/500`.
    3348 is the max-power word Apple exports, unchanged.
  - The firmware's power controller (`policy+0x04` = 16 sample period) reads that table next to
    per-state inputs that Apple exports for states 0–4 only (the ADT `perf-states` second column:
    450/675/781/815/881). Nothing is exported for index 5.
  - Whether the firmware's power or limit logic computes something from table[5] that crosses a
    bound between 948 and 996 is **not read**. It is the one host input that scales with the
    clock. Next RE target if the flight names `fw-event` or a firmware-ring site: the firmware
    readers of `meta+0x718` and `control+0x1028..0x1038`, and what Apple does at a state above its
    exported count.
- Job deadlines (`render_user_wait_ms`/`hard_ms`, `G5P_RU_V3_CAP_MS`, `G5P_RU_INPUT_MS`) are
  constant ktime milliseconds, and so are the 2 s lock bound and the heartbeat116 windows (1 s,
  16384 IRQs, 8192 events). A faster GPU only shortens the jobs.
- The PM pool is sized from the target's tiles (`g5p_ru_pm_blocks_for()`), not from the clock.
- The record-5 encoding at 996 is ordinary: `pll=332/4/2 rec4-dividers vco=1992`, inside Apple's
  VCO range (≤ 2160), readback match.
- So the 996-only behaviour is the firmware's or the hardware's, observed through one of the silent
  latches. Two kinds are possible:
  - firmware-written ring indices out of range (aux rings 0x71..0x73, or the event ring);
  - a firmware fault event.
- The F5 early start (`g5p_rv3_ahead_start()`) re-reads firmware ring state between its admission
  and its publication. GPU speed against host prep time can change which way that goes, but every
  failure there runs through the out-path terminal note and prints. It is therefore not the silent
  path, unless the A/B below says otherwise.
- **No behavioural fix was made.** No host-side derived constant was found to fix, and loosening a
  latch without knowing its site would mask a real limit. The next step after the flight depends on
  the site it names:
  - `r73b-aux-drain` + `R73B ring=… invalid indices`: read Apple's consumer for that ring in
    Ghidra (the R73B aux order is Apple's: four log lanes, events, statistics, trace). Find out
    whether iOS validates or masks the index, and what it does on a bad one, before changing ours.
  - `fw-event`: the type's own line follows (recovery, page request, channel error). The firmware
    stopped, which is a real limit at that voltage. iOS restarts the GPU; our recovery path applies
    (`g5p_rv3_recover()`), and the latch should then come with a `GPU-RECOVER` line.
  - `map` / `boot-command` / `recover`: the relatch or the power-on at state 5 failed. Check
    `GPUPERF poweron … ret=`.
  - `job` (with `G5P job failed … hardware=1`): it was not silent after all. The job's
    `RENDER-V3` lines say why.
